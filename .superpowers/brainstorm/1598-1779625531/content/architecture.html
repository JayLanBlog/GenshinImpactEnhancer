🏛️ 三种架构方案对比

已确定：C# .NET + WPF · 全功能复刻 · AI调参 · 极致UI · 性能仪表盘

A

📦 分层单体仓库（Layered Monorepo） ★ 推荐

单个 .sln 解决方案，按职责分层拆分为多个 Project。从下到上：
Native Layer（C++ DLL注入）→ Core Engine（C# P/Invoke 封装）→ Business Logic（配置/预设/更新）→ UI Layer（WPF 界面）
原项目用的就是这个模式，结构清晰，构建简单。

B

🧩 插件化架构（Plugin-Based）

核心启动器极简，ReShade / FPS Unlock / 3DMigoto 各自编译为独立 .dll，运行时动态加载。
通过 IPlugin 接口 统一管理生命周期。优势是引擎热插拔，但插件契约维护成本高。

C

🔀 多进程架构（Multi-Process）

每个引擎作为独立进程运行，通过 Named Pipe / Shared Memory 与启动器通信。
进程隔离好，挂了一个不影响其他。但注入场景下不适合——DLL 必须和目标进程同空间。

核心权衡

A. 分层单体 — 为什么最合适？
┌──────────────────────────────────┐
│  🖥️  Stella.Launcher (WPF UI)    │  ← 极致UI + 仪表盘 + AI面板
├──────────────────────────────────┤
│  🧠  Stella.Services             │  ← 业务逻辑：预设推荐 / 场景识别
├──────────────────────────────────┤
│  ⚙️  Stella.Core                 │  ← C# 封装 P/Invoke → C++ DLL
│  ├── ReshadeEngine               │
│  ├── FpsUnlockEngine             │
│  └── MigotoEngine                │
├──────────────────────────────────┤
│  🧬  Native (C++ DLL)            │  ← DX Hook / 内存修改 / 注入
└──────────────────────────────────┘
  • 所有 DLL 注入在同一个进程态，架构最自然
  • WPF UI 直接持有引擎引用 → 仪表盘数据零延迟
  • 单次编译 + 单包发布，用户下载即用
B vs C — 为什么不太适合

插件化的问题：

  • DLL注入引擎是强耦合的——都要 Hook DX Pipeline，强行拆分反而增加复杂度
  • 你不需要"热插拔"——玩家要么全开要么全关
  • 插件版本兼容矩阵是维护噩梦

多进程的问题：

  • DLL 必须注入到游戏进程空间，分离进程毫无意义
  • IPC 延迟会让仪表盘数据落后 50-100ms
  • 额外 ~200MB 内存开销
💡 结论： 分层单体是最佳选择。DLL 注入天然要求与目标进程同空间，强行拆分只会增加复杂度。原项目选这个不是偶然。
